Anatomie de la base, octet par octet

Toute la base tient dans un tableau de pages de 4 Ko en mémoire. Ce document suit une ligne depuis la commande insert jusqu'à sa place exacte dans une page, avec chaque taille, chaque offset et chaque octet perdu. Tous les nombres sont recalculés depuis les constantes de main.c et vérifiés avec sizeof / offsetof sur macOS arm64.

1 · La ligne : 293 octets

Le schéma est fixe : un entier et deux chaînes. Chaque chaîne réserve un octet de plus que sa longueur maximale pour le \0 final, d'où username[33] et email[256].

Pourquoi 296 et pas 293 ? uint32_t s'aligne sur 4 octets, donc le compilateur arrondit sizeof(Row) au multiple de 4 suivant. serialize_row copie champ par champ avec memcpy et ne copie donc jamais ces 3 octets : la forme sérialisée est plus compacte que le struct.

2 · Les 293 octets d'une vraie ligne

Voici exactement ce que insert 1 cstack foo@bar.com écrit dans la page. L'id est en little-endian (01 00 00 00). Après chaque \0, les octets restants sont copiés tels quels depuis le Statement sur la pile : leur valeur n'est pas définie.

4 · La table : 100 pointeurs, pages à la demande

Table ne contient pas les lignes : seulement un compteur et 100 pointeurs. Une page n'est allouée par malloc(PAGE_SIZE) que lorsque row_slots y accède pour la première fois ; avant cela le pointeur vaut NULL.

6 · Le trajet d'un insert

sqlite > insert 1 cstack foo@bar.com
read_input        getline → InputBuffer.buffer, '\n' remplacé par '\0'
prepare_statement strncmp("insert", 6) → prepare_insert
prepare_insert    strtok ×4 · atoi(id) · id < 0 ? · strlen ≤ 32 / ≤ 255 ?
                  strcpy → Statement.row_to_insert            (pile, 300 o)
execute_insert    num_rows ≥ 1300 ? → EXECUTE_TABLE_FULL
row_slots         page = num_rows / 13 · malloc si NULL · + (num_rows % 13) × 293
serialize_row     memcpy 4 @0 · memcpy 33 @4 · memcpy 256 @37 (293 o)
                  num_rows += 1 → "Executed."

select fait l'inverse : pour chaque i < num_rows, deserialize_row recopie les 293 octets dans un Row local et l'affiche. C'est un balayage complet à chaque fois : pas d'index.

7 · Limites et points à surveiller

  • Tout est en RAM. .exit libère les pages ; rien n'est écrit sur disque.
  • 7,01 % de chaque page est perdu (287 octets), soit 28 700 octets sur une table pleine.
  • Largeur fixe. Une ligne coûte toujours 293 octets, même pour insert 1 a b.
  • Octets non initialisés. Ce qui suit le \0 vient de la pile. Le jour où les pages iront sur disque, ces octets y partiront aussi : un memset de row_to_insert avant le strcpy les fixerait à zéro.
  • atoi ne détecte pas un id hors de int ni un id non numérique (insert abc … donne id 0).
  • Ordre de libération. free_table s'arrête au premier pointeur NULL ; c'est correct tant que les pages sont allouées dans l'ordre, ce que garantit l'insertion séquentielle.
